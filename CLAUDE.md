# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

The `Makefile` wraps the common tasks:

- `make check` — `cargo check` for the workspace, plus separate checks for `wezterm-escape-parser`, `wezterm-cell`, `wezterm-surface` and `wezterm-ssh` (these have feature/`no_std` setups that a workspace check doesn't cover).
- `make build` — builds the `wezterm`, `wezterm-gui`, `wezterm-mux-server` and `strip-ansi-escapes` binaries. Pass `BUILD_OPTS=--release` for release builds.
- `make test` — `cargo nextest run`, then `cargo nextest run -p wezterm-escape-parser` (that crate is `no_std` by default, so it is tested on its own).
- `make fmt` — `cargo +nightly fmt`. CI runs `cargo +nightly fmt --all -- --check`, so formatting must use nightly rustfmt.
- `make docs` / `make servedocs` — build or live-serve the docs site (`ci/build-docs.sh`). This also runs `gelatyx` with `ci/stylua.toml` over Lua code blocks in the docs and fails if they aren't formatted.

Single tests:

```console
$ cargo nextest run -p term <test_name>     # or: cargo test -p term <test_name>
```

Running the GUI during development:

```console
$ cargo run --bin wezterm-gui -- start --always-new-process      # keeps mux logs from hiding in an older background process
$ cargo run --bin wezterm-gui -- --config-file ./test-conf.lua   # use a test config
```

Other scripts:

- `ci/update-derived-files.sh` regenerates shell completions in `assets/shell-completion/` and the CLI `--help` synopses and default key tables in `docs/examples/`. Run it after changing CLI arguments or the default copy/search mode key tables (needs a debug build in `target/debug`).
- `ci/update-cargo-deps-with-cooldown.sh` is the way to update dependencies: it runs `cargo cooldown update`, which follows `cooldown.toml` (crate versions must be at least 14 days old). Don't run plain `cargo update`.
- `.github/workflows/gen_*.yml` are generated by `ci/generate-workflows.py`. Edit the Python script and regenerate; don't edit the generated files.
- Platform build dependencies are installed by `./get-deps`.

## Architecture

WezTerm is a Cargo workspace of many crates. The main layers, from the bottom up:

- **Escape parsing and terminal model.** `vtparse` is the low-level VT state machine. `wezterm-escape-parser` turns it into typed actions (CSI, OSC, DCS, etc.). `term` is the terminal emulator model (`Terminal`, `TerminalState`, screens, scrollback). It has no windowing code and targets xterm compatibility (https://invisible-island.net/xterm/ctlseqs/ctlseqs.html). Escape sequence work belongs in `wezterm-escape-parser` and `term`. Cell and line storage live in `wezterm-cell` and `wezterm-surface`.
- **termwiz** is a standalone, separately published terminal library (input decoding, terminfo, line editor, widgets, render surfaces). It is used by wezterm and by outside projects, so keep its public API stable.
- **Mux.** `mux` owns the model of windows → tabs → panes and the `Domain` abstraction that spawns panes (local PTY via `pty`, SSH via `wezterm-ssh`, tmux control mode, serial, remote mux). `codec` defines the PDU wire protocol for the multiplexer. `wezterm-mux-server-impl` serves that protocol; `wezterm-client` implements client domains/panes that talk to a remote mux. `wezterm-mux-server` is the headless server binary.
- **GUI.** `window` is a cross-platform windowing layer with backends in `window/src/os/` (macos, windows, x11, wayland). `wezterm-font` handles font discovery, shaping and rasterization. `wezterm-gui` is the GUI front end: `termwindow/` holds the per-window state, input handling and rendering (OpenGL and WebGPU paths, shaders in `*.glsl`/`shader.wgsl`), and `overlay/` holds modal UIs such as the launcher, copy mode and quick select.
- **Binaries.** `wezterm` is the CLI (`wezterm cli ...`, `imgcat`, `ls-fonts`, etc.). GUI subcommands such as `start`, `ssh` and `connect` are delegated to the `wezterm-gui` binary (`delegate_to_gui` in `wezterm/src/main.rs`).
- **Config and Lua.** `config` defines the `Config` struct and related types. Fields use `wezterm-dynamic`'s `FromDynamic`/`ToDynamic` derives with `#[dynamic(default = "...")]` attributes, which convert between Lua values and Rust. Lua functions exposed to config files live in small crates under `lua-api-crates/` (kept separate to help build times) and are registered in `env-bootstrap` (`register_lua_modules`). GUI-specific Lua objects live in `wezterm-gui/src/scripting`.

## Tests

Terminal behavior tests live in `term/src/test/` (`csi.rs`, `c0.rs`, `c1.rs`, `selection.rs`, `image.rs`). Use the `TestTerm` helper in `term/src/test/mod.rs`: feed bytes with `print` and check the screen with `assert_visible_contents`. Add comments to tests that explain their intent (requested in `CONTRIBUTING.md`). `test-data/` holds manual test scripts and sample text for rendering checks.

## Docs and changelog

- User docs are in `docs/` (MkDocs). Config options and Lua APIs are documented under `docs/config/lua/`. New or changed behavior should come with docs.
- Add user-visible changes to the "Continuous/Nightly" section at the top of `docs/changelog.md`.

## Conventions

- Commit subjects are prefixed with the area or crate, e.g. `mux: ...`, `wezterm-gui: ...`, `term: ...`, `docs(ssh_backend): ...`, `deps: ...`.
- The default branch is `main`.
